== Purpose

This document specifies the tests for the firmware of the OrgPort display node (CANopen Node
0x10, Riverdi 7" STM32H757 board). It defines what is tested, how, in which environment, with
which pass/fail criteria and with which evidence, so that the results recorded in the test
report (TR-DISP-002) can be reviewed and repeated.

The firmware under test integrates:

* the TouchGFX operator interface (18 screens and shared containers);
* the CANopen interface to the main controller (Node 0x04, NXP S32K312);
* CAN traffic logging to the microSD card;
* the copy of the session logs to a USB pen drive.

== Scope

=== In Scope

* All display-owned firmware: `CM7/app`, `CM7/app_middleware`, `CM7/platform_if`,
  `CM7/src/canopen` (port, bridge, object dictionary), `CM7/TouchGFX/gui` (Model, Views,
  Presenters, containers) and the user sections of the CubeMX code.
* The CANopen interface contract between Node 0x10 and Node 0x04 (PDO, SDO, heartbeat, NMT,
  operator inputs, setpoints).
* Behaviour of the display in combination with the main controller, where the outcome is visible
  on the display or on the bus.

=== Out of Scope

* TouchGFX-generated code, the CANopenNode library, the ST HAL, FatFs and USB host libraries, and
  the third-party keyboard component (only their integration is tested).
* Internal behaviour of the main controller (Node 0x04). Defects of Node 0x04 found while testing
  the display are recorded and handed to the Node 0x04 team.
* Clinical validation of setpoints, timings and alarm limits.

=== CANopen Interface with Node 0x04

[cols="1,1,1,3",options="header"]
|===
|Object |COB-ID |Direction |Content
|Heartbeat |0x710 |Tx |Producer 500 ms
|Heartbeat consumer |0x704 |Rx |Node 0x04, timeout 600 ms
|RPDO1 |0x181 |Rx |workflow_state, alarm_flags (32 bit), session_hours, gps_fix
|RPDO2 |0x281 |Rx |perfusate and chamber temperature (x0.01 degC), humidity, bubble, level
|RPDO3 |0x381 |Rx |perfusate/chamber temperature 2, accelerometer, hall, compressor
|RPDO4 |0x481 |Rx |GPS latitude and longitude (float32)
|RPDO5 |0x581 |Rx |Debug event (event id, severity, source, payload)
|RPDO6 |0x681 |Rx |Boot health (reset reason, safe-mode reason, boot number)
|RPDO7 |0x781 |Rx |Pressure 1/2, pump RPM, priming status, phase seconds left
|TPDO1 |0x190 |Tx |confirm_counter, confirmed_state, auth_status, organ_type, mode, organ_weight
|SDO server |0x610 / 0x590 |Rx/Tx |Access to the display OD
|SDO client |0x604 / 0x584 |Tx/Rx |Writes to Node 0x04: 0x2200 subs 7-12 (acknowledge,
pause-resolve, motor diagnosis), 0x2201 (setpoints)
|===

RPDO1-RPDO4 use a 3 s event-timer timeout. The display does not wait for NMT Start: it goes
Operational by itself when the Node 0x04 heartbeat reports Operational.

[[evidence-strategy]]
=== Evidence Strategy

Screen evidence is collected *per screen state, not per test case*. A fixed catalogue of
reference figures (FIG-xxx, see <<evidence-catalogue>>) covers every screen and popup state once.
Each test case names the figures that show its expected result. One screenshot can therefore serve
several test cases, and the number of images stays small.

* Figures are stored as `test_report/evidence/<FIG-ID>.png`. Until a figure is captured, the test
  report shows a marked placeholder in its place. A missing figure does not change a test result;
  the result is decided by the expected result of the test case.
* Alarm and fault conditions that cannot be produced on the real hardware (for example motor
  failure, refrigeration failure, pressure sensor faults) are produced with the Node 0x04 bench
  simulator. Their evidence is the bench CAN trace (`m1_bench_sim/logs`) or the SD card log, plus
  the representative figure of the alarm centre (FIG-ALM-01). Annex A lists every alarm bit that
  TC-ALM-002 covers.
* Bus-level results are evidenced by script console output, CAN traces or SD card logs, verified
  with `check_canlog.py` where applicable.

=== Defect Management

Every failed test case is linked to a defect in Jira project ORPT (ORPT-151 onwards for this
campaign). Defects of Node 0x04 found during display testing are raised in the same project and
assigned to the Node 0x04 team.

[cols="1,3",options="header"]
|===
|Severity |Definition
|Critical |Prevents a session from starting or continuing, or can mislead the operator about the
organ state; no workaround
|Major |Function does not work as specified or wrong data is sent/shown; workaround exists
|Minor |Cosmetic or usability issue without effect on data or control
|===

=== General Preconditions

. The DUT runs the build identified in the test report, flashed with STM32CubeIDE.
. Unless a test case says otherwise, the SD card is inserted and no USB stick is connected.
. Bench tests: the bench simulator is started before the DUT is powered; the real Node 0x04
  never sends NMT commands, so protocol tests that depend on that behaviour use `--no-nmt-start`.
. HIL tests: Node 0x04 runs its integration release, built without test bypass macros (see OI-16).
. The TouchGFX simulator tests use the simulator build of the same source.

=== Entry, Suspension and Exit Criteria

[cols="1,3",options="header"]
|===
|Criterion |Definition
|Entry |Both builds pass (TC-BLD-001/002); the DUT boots to Screen 1; test tools available
|Suspension |A Critical defect blocks the remaining cases of an area; the SLCAN bridge stops
responding (restart the bridge and repeat the affected case)
|Resumption |Defect fixed or workaround agreed; tools working
|Exit |All test cases executed or justified as BLOCKED; all FAIL results have a defect; no open
Critical defect for release
|===

=== Pass / Fail Criteria

A test case passes when every expected result is met. Any deviation is a failure and is recorded
with a defect. A test case is BLOCKED when a feature or dependency it needs does not exist yet
(reference to the open item), and NOT RUN when it has not been executed on the build under test.
