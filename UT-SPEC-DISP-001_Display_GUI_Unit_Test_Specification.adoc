== Purpose

This document defines the unit-level test specification for the Display GUI module of the OrgPort Riverdi HMI node (Node 0x06), implemented in TouchGFX.

The purpose is to verify that:

* the `Model` singleton stores, truncates, and returns data correctly;
* each screen's `View` logic (state machines, boundary clamping, colour/threshold rules, navigation) behaves correctly under nominal, boundary, and fault-injection conditions;
* screen-to-screen navigation matches the intended workflow; and
* shared containers (`TopStatusBar`, `AlarmMessageTemplate`, `Keyboard`) behave correctly across all screens that use them.

This specification covers **all 18 screens** currently present in the `display/gui` project (`screen1_screen` … `screen18_screen`), the `Model`/`ModelListener` data layer, and the three reusable containers.

== Scope

This specification covers white-box and black-box unit tests for:

* `gui/src/model/Model.cpp` (data layer)
* `gui/src/containers/TopStatusBar.cpp`, `AlarmMessageTemplate.cpp`, `Keyboard.cpp`
* `gui/src/screen1_screen` through `gui/src/screen18_screen` (View + Presenter logic only)

It does **not** cover:

* Rendering correctness of the `gui_generated` Designer-generated base classes (`*ViewBase.cpp`) — these are treated as trusted, tool-generated code, analogous to how <<UT-SPEC-MW-001>> excludes FreeRTOS kernel correctness.
* EVE/BT817 coprocessor driver behaviour, SPI/display bring-up, or touch-controller correctness — covered by the Riverdi middleware test specification (not yet written; see <<open-items>>).
* CANopen RPDO/SDO integration between the Riverdi node and the S32K312 node — covered by the Integration Test Specification and by `CIOET-ORGPORT-SWRS-RVD-2026-001`.
* Third-party component internals: `Keyboard` is attributed to a third-party author (CodeDog, 2024) in its file header; only the integration points used by this project (`edit()`, `targets()`, `toUTF8()`, caps-lock, backspace) are tested, not the full QWERTY layout engine.

=== General Preconditions (apply to all test cases unless overridden)

. The Simulator (or target board) is freshly restarted before each test suite execution, so `Model::Model()` runs its default-constructor initialisation (`selectedOrgan = ORGAN_NONE`, `activeTargetTemperature = 8`, `activeTargetPressure = 0`, all string buffers empty).
. Screen navigation starts from Screen 1 (Startup) unless a test case states it starts from a specific screen — reaching later screens in isolation requires either replaying the preceding screens or a debug jump (`application().gotoScreenNScreenNoTransition()` called directly from a test harness).
. All wildcard buffers are in their designer-default (unformatted) state at the start of each screen's `setupScreen()` unless stated otherwise.
. Test results are recorded in the Test Execution Report (document TER-DISP-001, to be created).

=== Pass / Fail Criteria

A test case passes when *all* expected results stated for each step are met with no deviation. Any single deviation constitutes a failure and must be recorded with an incident report reference.

[[automated-test-execution-procedure]]
=== Test Execution Procedure

Two execution lanes are used, mirroring the Automated/Manual split in <<UT-SPEC-MW-001>>, adapted for a GUI codebase where most CUTs are tightly coupled to TouchGFX widgets:

**Lane A — Automated (Host, logic-only).**
Test cases whose CUT is pure C++ logic with no widget rendering dependency (e.g. `Model` getters/setters, PIN-buffer arithmetic, temperature/volume boundary clamps, alarm-sequencing counters) are extracted into a Unity test binary that links the relevant `.cpp` file(s) directly, stubbing only `touchgfx::*` calls that the logic path does not need. All Lane A cases for a given screen/module are run in a single Unity binary execution; one console log is captured as evidence for that module's Lane A cases.

**Lane B — Manual (Simulator or Target).**
Test cases whose CUT includes widget visibility, colour, invalidate(), or touch-input dispatch are executed by hand:

. Launch the TouchGFX x86 Simulator (or flash the target board).
. Navigate to the screen under test by replaying the preceding screens (see <<general-preconditions>> above), or by using a debug build with a screen-jump menu if available.
. Perform the interaction described in the test case's Test Steps.
. Visually confirm the Expected Result (widget visibility, text content, colour, transition target).
. Record Pass/Fail and, for target-only cases, capture a photo or logic-analyser trace as evidence.

Each test case below states its Lane (**A** or **B**) in the Execution column of the Test Traceability Matrix.

== Module: Model — Data Layer

=== Overview

`Model` is a singleton (`Model::getInstance()`) that stores organ selection, active target temperature/pressure, preservation mode, six fixed-size string fields (organ ID, weight, harvest hospital, destination institution, blood type, cross-clamp time), and the final elapsed-time snapshot used on the Transport Summary screen. All string setters use `std::strncpy` into fixed buffers and manually null-terminate the last byte.

[[manual-hardware-test-cases-summary]]
== Manual (Lane B) Test Cases Summary

Test cases marked **B** in the Test Traceability Matrix above require the TouchGFX x86 Simulator or the Riverdi target board and are executed by hand, per the <<automated-test-execution-procedure,Test Execution Procedure>>. They are concentrated around: screen navigation/transitions, colour and visibility state confirmed by eye, and touch-input dispatch (button taps, card selection, keyboard entry). Refer to each test case's own Test Steps for the exact interaction sequence.

Lane A (Automated) test cases are, by contrast, concentrated in: `Model` data-layer behaviour, boundary/clamp arithmetic (temperature, pressure, volume, PIN length, alarm counters), and state-machine transition logic that does not itself depend on reading rendered pixels.
